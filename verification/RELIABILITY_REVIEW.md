# 信頼性レビュー（1.1.2）

レビュー日: 2026-10-09（日本時間）。AudioSystem の定数・UserService reflection・AIDL・既存 UI と手動優先の方針を維持した。

## 発見した問題と修正

| 優先度 | 発生条件と原因 | 修正 |
| --- | --- | --- |
| 高 | set が成功を返した後、読み戻しが失敗／不一致でも先に active を保存していた。pending も UI では enabled と表示していた | active は成功応答と実値 0 の確認後にコミット。pending は未確認として表示し、再適用を禁止 |
| 高 | 保存された active と実値が不一致のまま再有効化すると、最初の original を実値で上書きできた | 未完了・不一致・不正な復元記録を保持し、再有効化を止める |
| 高 | 監視 coroutine のキャンセル時に、IO 上の同期 Binder 書き込みはまだ進行している可能性があった | Controller 自身の Mutex と NonCancellable な書き込みトランザクションで、結果確認と保存まで排他を維持 |
| 高 | 前面アプリを調べてから操作ロックを待つため、待ち時間中に判定が古くなり得た | ロック取得後に観測。自動復元のトランザクション内でも直前に再確認し、戻り／未知観測なら復元を取り消す |
| 高 | 接続初期化のジョブが最初の監視操作より後に gate を reset し、短いホーム遷移で即復元し得た | 接続 session の実値確認終了まで監視操作を待つ。既存自動記録は gate に引き継ぐ |
| 中 | UserService death／接続タイムアウト後、手動モードでは監視ループによる再接続がなかった | Manager が5秒後の再接続を管理。新しい接続 session ごとに実値を読み直す |
| 中 | unbind(remove=true) だけでは Shizuku API のローカル接続リストが残る | サーバーからの削除とローカル listener の除去を区別。二重 callback と古い connection は無視 |
| 中 | 初期化前の Binder に対して permission 判定を行い、未許可と表示し得た | Binder received 完了状態を区別。初期化中の権限は確認不可と表示 |
| 中 | 空の topActivity を対象外と見なし、取得の取りこぼしで復元し得た | 空は未知観測。退出時間を積算せず、適用／復元の根拠にしない |
| 中 | 手動 OFF が古い targetMatched を使って自動へ引き継ぎ得た | 手動 OFF 時点で前面アプリを再取得 |
| 中 | 監視終了と再開始の重複、古い session の初期化ジョブが状態を変更し得た | 監視 generation と接続 session を検証。新しい監視があれば古い cleanup は復元しない |
| 中 | screen interactive でも端末がロックされている場合にカメラ task を有効対象にできた | Keyguard のロック状態も確認し、自動分だけ解除する |
| 中 | 読み込み失敗後も UI に直前の実値を残し得た | 確認できない snapshot を無効化し、エラーと接続状態を通知 |

## 永続記録の意味

- `originalForceUse`: 最初に取得した復元先。読み戻しで復元を確認するまで保持する。
- `overrideActive`: 成功応答と適用後の読み戻しを確認済み。実値 0 と有効な original が揃って初めて UI の enabled になる。
- `changePending`: 書き込み前に保存する回復用の意図。応答喪失・読み戻し失敗・保存失敗・process kill に備える。適用完了の証拠ではない。
- `overrideOwner`: pending の新規適用では回復処理の担当を表す。有効状態の所有権変更は実値確認後に行う。自動処理は手動所有を奪わない。手動 OFF による明示的な引き継ぎだけ許可する。

復元対象は 0 / 11 のみ。不正な original や UNKNOWN を 11 へ置換しない。失敗応答の場合も実値が変更前と同じと確認できた場合にだけ pending を取り消す。
同じ active を再有効化した場合は実値を確認し、不要な set を行わない。復元記録のない OFF／復元はエラーにし、推測で書き込まない。

## テスト範囲

従来の入力制限・正常適用／復元・所有権・ForegroundGate テストに加え、Controller の応答喪失、初回 get と読み戻し失敗、不一致、保存失敗、stale record、元値欠損、キャンセル、同時操作、再生成後の回復を検証。

Robolectric と偽 Shizuku 境界では、Binder death、Shizuku 停止／再起動、タイムアウト、重複 bind／callback、権限失効、古い callback、UserService 再接続を検証。
Engine の実際の監視ループでは、Camera A → home → Camera B、対象間移動、未知観測、復元直前の対象への戻り、ロック／screen OFF、監視再開始、再接続後の復元、手動優先を検証。

## 残る構造上の制約／実機確認

- 本レビューでは端末操作・実機テストは行っていない。偽 Binder による JVM テストは、実際の Shizuku サーバーや OEM の挙動の確認ではない。
- アプリと UserService が共に終了した瞬間や Shizuku が停止中は、復元用 API を呼べない。DataStore 記録を保持し、次回接続時に実値と照合する。手動 Override は既存仕様どおり明示的な OFF／復元まで維持する。
- 同期 Binder 呼び出しに中断を強制できない。NonCancellable の処理中にサーバーが応答せず停止した場合、操作ロックが待機し続ける可能性がある。単純な timeout でロックを解放すると、遅れて完了する書き込みとの競合を再導入するため行っていない。
- AudioSystem は端末全体の設定で、他アプリ／OS の変更を排他的に止める API や compare-and-set はない。読み取り・永続保存・書き込みの間の外部変更は完全には排除できない。
- 約250msの監視周期より短い動作は観測されない場合がある。退出待ちの取り消しは最後に観測した値に基づき、最後の確認から native set までの瞬間の遷移も完全には検知できない。
- `getTasks(1).topActivity` は焦点・可視性・カメラ使用の証拠ではない。Recents、PiP、分割画面、複数画面、ロック画面カメラは OEM と Android バージョンごとに検証が必要。画面 OFF／ロックは同じ自動復元方針だが、周期と0.8秒の退出待ちにより即時ではない。
- 空の task 結果が継続すると誤復元を避けるため自動 Override を保持する。手動の復元ボタンで停止・復元できる。
- hidden API の存在・権限・戻り値・反映タイミング、Shizuku 派生版での認可情報と接続先の食い違い、OS による foreground service 終了後の再開は実機で確認する必要がある。
